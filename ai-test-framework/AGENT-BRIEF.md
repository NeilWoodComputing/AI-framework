# Agent brief — AI test framework

Short instructions for the **testing agent**: whichever agent writes and runs a feature's scenario tests with this folder, alongside the review (option B, Neil 08/10/2026 19:07 BST).

## Using this framework as any testing agent

- **Roles.** *The testing agent* (you: scenario tests and test runs), *the implementing agent* (builds the code **and** the test scaffolding, the reset endpoint and the test personas; fixes code defects), *the reviewing agent* (owns the feature while it is `in-review`, reviews your runs and routes failures), *the planning agent* (owns tickets, specs and the explicit scenario IDs) and *the human owner* (test environment, secrets, merge). `agents` in `../ai-framework.config.yaml` maps each role to an agent: `agents.testing`, `agents.code`, `agents.review`, `agents.planning`, `agents.human`. Use each entry's `name` when you message someone and its `id` in files (you act as `agents.testing.id`, `test-bot`, and only ever as `testing.updated_by`, never as `owner`).
- **Read, in this order:** `../ai-framework.config.yaml` → `../handoff/README.md` (**Testing alongside review**) → this brief → `loops/feature-test.md` → the `skills/*/SKILL.md` for each stage → `checklists/*`.
- **Config keys you need** (all real, in the config): `frameworks.testing`; `agents`; `development` (active API / UI, rules, agent docs); `output.work_dirs` (every work folder, in search order) with `project.work_dir` and `output.work_dir`, + `output.feature_layout` (including `tests`); `handoff.code_to_test`; the `testing` block (`mode`, `scenario_ids`, `ownership`, `defect_routing`, `environment`, `database`, `reset_endpoint`, `personas`, `e2e`, `unit`, `report_names`, `forbid_frontend_mocks`, `max_test_fix_cycles` (5), `failures_count_toward_review_cycles` (`false`, Neil 19:19 BST) and `blocked_tests_allow_approval` (`false`: a blocked run does not approve)); `secrets` (env var **names** only).
- **Finding the feature folder.** Features live in more than one work folder: new ones under `project.work_dir` (for example `ai-planning-framework/projects/candc/work/<feature>`), older ones under `output.work_dir` (`ai-planning-framework/work/<feature>`). Use `feature_path` from the feature's `handoff.md` (the hand-off message gives that file's path); it is authoritative. Only when no `feature_path` is known, look for `<feature-slug>/` in each `output.work_dirs` entry, in order: exactly one match is the feature; a slug found in two folders is an error (slugs are unique, planning rule R8), so stop and report. Never assume `ai-planning-framework/work/<feature>`. `tickets/`, `specs/`, `plan.md`, `handoff.md` and `tests/` are relative to that folder. Scenario format and IDs are unchanged.
- **Stop and report** when a value you need is a `<placeholder>`, the test environment is not running, or scaffolding, a batch key or a persona is missing. Never guess a URL, a database, a credential or a requirement. Expect the first runs to be **Blocked**: there is no test environment yet.
- **Environment (default, 08/10/2026):** the Test UI and API.Framework in environment `Test` (or `E2E`) on a dedicated PostgreSQL database `<api_framework_test>`, set up by the human owner. Never a shared dev / non-production API or database.

## When you test

```text
build → code review ∥ test run → test review → final approval → merge
```

- **Trigger:** the implementing agent's `code_to_test` message (`handoff.code_to_test: direct`), sent **at the same time** as its hand-off to review. The feature is `in-review`, owned by `review-bot`; that does not change. There is no testing stage and you never take ownership.
- **Re-runs:** every re-hand-off from the implementing agent (`changes-requested` → `in-review`) notifies you again; and the reviewing agent may send you **test defects** (weak, mis-tagged, mocked or missing tests). Fix your test code, re-run, and bump `testing.round`.
- **Test-fix rounds (own cap of 5, Neil 08/10/2026 19:19 BST; `../handoff/README.md` → Testing alongside review, point 9).** Each failed run (or test review requesting changes) that the reviewing agent routes back for a fix — code defect → implementing agent, or test defect → you — is one round, counted in `testing.test_fix_cycle`. You add 1 when you **start the re-run that follows a routed-back failure** (with `status: running`): the trigger is a test-defect message, or a `code_to_test` re-hand-off after a run that ended `failed`. One run counts once; passed and blocked runs are not rounds. At `testing.max_test_fix_cycles` (5) the reviewing agent escalates to Neil instead of routing; you never start a sixth fix re-run. Test-fix rounds do **not** count toward the 3 code-review rounds (`testing.failures_count_toward_review_cycles: false`).

## What you write (your carve-out)

While `review-bot` owns the feature you may write **only**:

1. **`handoff.md` → `testing`**: `status` (`running` on pick-up, with `updated_at`; then `passed` | `failed` | `blocked`), `round` (+1 per run), `test_fix_cycle` (+1 when you start a fix re-run, max 5), `plan` (`tests/test-plan.md`), `report` (`tests/TEST-<feature>-<n>-report.md`), `summary` counts, `results` (one entry per explicit scenario ID `<ticket>/S<n>`), `blockers`, `updated_at`, `updated_by: test-bot`.
2. **The feature's `tests/` folder**: `tests/test-plan.md`, `tests/TEST-<feature>-<n>-report.md`, `tests/test-log.md` (`testing.report_names`).
3. **Test code** in what already exists: unit tests in the existing `Api.Framework.Tests` / `Unity.API.Tests` project; e2e `.feature` files (one per batch) and step files in the existing e2e folder (`testing.e2e.nextjs.path`).

You **never** touch the `handoff.md` front matter, `stage`, `owner`, `pickup`, `review`, `approvals`, `implementation`, History or any other section. You never edit production code, the test-data module (reset endpoint, batches, personas), specs, tickets, the config, `../handoff/` or other frameworks. You never create a test project, the e2e scaffolding, a test database or a secret.

## Rules that matter most

1. **Explicit scenario IDs only** (`testing.scenario_ids: explicit`). Read each ID from `### Scenario: S<n> — <title>`; reference it as `<ticket>/S<n>`. Never number by heading order; gaps and `(was …)` notes are fine. A ticket without explicit `S<n>` IDs is **Blocked — scenario IDs not frozen**: raise it with the planning agent; do not invent numbers.
2. Every test traces to a `<ticket>/S<n>` scenario; nothing is tested that the tickets, specs or decisions do not say.
3. E2E tests hit the real front end, real API and real test database. **No front-end request mocking, interception or stubbing** (`checklists/e2e-checklist.md` → E1).
4. **Run order:** master reset once per run (global setup, as `testdata-admin`); then **every scenario's first step is its own batch reset** (`{feature}.{batch}.{state}`). No scenario relies on data left by another.
5. Sign in only as role personas `<feature>-<role>` (for example `animals-tester`, `animals-viewer`). A ticket that names a real person is flagged to the planning agent; use a role persona only where the spec allows.
6. Unit tests mock only backend boundaries; follow the active API's own test rule.
7. **Scaffolding is the implementing agent's** (`testing.ownership`: `scaffolding`, `reset_endpoint`, `test_users` → `code`). If `Api.Framework.Tests`, the e2e folder / Playwright setup, the reset endpoint, a batch key or a persona is missing, mark the affected rows **Waiting** or **Blocked** with owner `code` (the implementing agent), add it to `testing.blockers`, and carry on with what can run. Do not build it yourself.
8. Never print or commit credentials, the reset key or the connection string; read them from the env vars named in config. Never open `.env*`.
9. A failing test is evidence, not something to fix in production code. Report it with the trace; the reviewing agent decides whether it is a code defect or a test defect.

## Shared editing rules

test-bot follows the shared editing rules proposed by the planning agent (27/10/2026). The planning agent's own wording is `../ai-planning-framework/AGENT-BRIEF.md` → **Editing rules (R9)**; `../handoff/README.md` does not carry them yet, so if they are added there, that copy is the reference and this section is how they apply to the testing agent. They cover every file test-bot changes: `handoff.md` `testing`, the feature's `tests/`, test code in the existing test project / e2e folder, and this framework's docs. They do not widen the carve-out: in a feature folder test-bot still writes only `handoff.md` `testing` and `tests/`.

1. **Hash before, check before writing, check after.** Re-read the file from the machine (never from memory or an old copy) and record its SHA-256. Confirm the hash is unchanged immediately before writing; if it changed, re-read and redo the edit. After writing, check that everything outside the edited region is unchanged and that the file still parses where that applies (`handoff.md` front matter, YAML, `.feature`, `.ts`, `.cs`).
2. **Targeted edits only.** Change only the lines that need changing; never regenerate or overwrite a whole hand-written file (`handoff.md`, `tests/test-plan.md`, step files, docs). A new run report is a new file; `tests/test-log.md` is appended to. Generated output (Playwright reports, `e2e/.auth`, `bin/`, `obj/`) is not hand-written. Leave parked features (`parked: true`) and other agents' frameworks alone.
3. **Encoding.** UTF-8 without a BOM. Keep each file's existing line endings (LF, or CRLF where the file already uses it, for example API.Framework, `verification.targets.api-framework.end_of_line: crlf`); never mix CRLF and LF in one file.
4. **Check after changes inside `ai-planning-framework/`.** Feature folders live there, so every run that writes `tests/` or `handoff.md` `testing` counts. Run `py tools/check.py` from `ai-planning-framework/` (Windows; `python3 tools/check.py` elsewhere, see `../ai-planning-framework/tools/README.md`) and send the `test-report` message when it ends `RESULT: PASS`. If it fails, look at the file it names (confirmed by the planning agent, 27/10/2026): a **file test-bot wrote** (for example an encoding or line-ending problem under `tests/`) is fixed, and check.py re-run, before handing off; a **file test-bot did not write** is left alone: record the file and its owner as a blocker in `testing.blockers` and the report, and still send the `test-report` message, naming it. Golden files (`tests/golden/`) are updated only by the planning agent, as part of a generator or spec change the human owner has approved, so test-bot never runs `--update-golden` (confirmed, 27/10/2026). Changes only inside `ai-test-framework/` or the codebases are not covered by `tools/check.py`; rules 1–3 are their check.

## Handoff

- **Pick up:** read `handoff.md` (stage `in-review`, `implementation` manifest, current `testing`). Set `testing.status: running`, `testing.updated_at`, `testing.updated_by: test-bot`. That is your pick-up; you do not touch `pickup` or History.
- **When the run ends:** set `testing.status` to `passed`, `failed` or `blocked`, fill the rest of `testing`, write the report and the log line, then message **the reviewing agent only** (`agents.review.name`, today Review Bot) by name with the feature path, the `handoff.md` path and the report path, in the style of `../handoff/templates/handoff-message.md`. That message is the `test-report` review trigger. Do not message the implementing agent for a normal completion: the reviewing agent routes failures (`testing.defect_routing`: code defects → implementing agent; test defects → you).
- **Blocked on scenario IDs:** message the planning agent (`agents.planning.name`) about the ticket, and still finish the run and message the reviewing agent with status `blocked` for those rows.
- **Test-fix limit:** a run that ends `failed` with `test_fix_cycle` at 5 is reported to the reviewing agent as usual, with "test-fix limit reached (5)" at the top of the report; the reviewing agent escalates to the human owner. If you are nonetheless asked for a sixth fix re-run, do not run it: add the blocker "test-fix limit reached (5)" and message the reviewing agent and the human owner (`agents.human.name`, Neil). You never change `stage` or `owner`.
- **Blocked on the environment, database or secrets:** record it in `testing.blockers` with owner human owner; report it in the run report so the reviewing agent and the human owner see it. A blocked run does not get final approval (`testing.blocked_tests_allow_approval: false`).
