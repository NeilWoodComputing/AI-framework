# Rules

The framework's rules, stated once. Skills, the loop and the brief refer to them by ID (e.g. **R1**)
instead of repeating them. Where a rule has a profile switch (`rules.<key>` in the active project profile), it is **on** unless that profile sets it to `false`.
Why each rule exists, and when it was decided: `DECISIONS.md`.

| ID | Rule | Profile switch | Enforced by |
|----|------|----------------|-------------|
| **R1** | **List pages vs modals.** A feature list with its own route **is a page** (`Paginated Grid`): its search / filters and results sit on the page. No initial modal for the list, no auto-open, no landing page whose only job is to open the list. Modals are only for create / edit forms (Form Modal, Wizard Modal), imports and confirmations. `Embedded Grid Modal` (older specs: `Modal`) is only for a list genuinely embedded in another page's flow (e.g. Book Copies opened from a Book). | `list_pages_not_modals` | Schema (`route` required on a Paginated Grid); review |
| **R2** | **Paginated Grid ticket split.** One Paginated Grid spec / Excel gives two tickets: (a) **page**: route, nav link, permission gate, no-permission message, page layout and search / filter area, hosting the grid and the create / edit form modal; (b) **paginated grid**: columns and population, sorting, paging, the row actions menu and the empty state. The page ticket depends on the grid ticket. Switched off: one ticket covering both parts. | `paginated_grid_two_tickets` | generate-tickets checklist |
| **R3** | **DB mapping on every control.** Wizard, Form Modal and Basic Form controls and Import template columns carry **Service**, **Target DB Table** and **Target DB Column**; grid results columns carry **Population Source** (`Table.Column`). `include_service_db_columns: false` only for a rough UI sketch, never for hand-off. | `service_db_columns_required` | Schema (required fields) |
| **R4** | **Never invent mappings.** Do not invent Service, Target DB Table, Target DB Column or Population Source values that are not in the linked YAML / Excel. If one is missing, fix the spec (`generate-ui-spec`) and regenerate before tickets or publishing. | — | generate-tickets / publish-tickets checks |
| **R5** | **Tickets only from `tickets/`.** Tracker items are created only from `<feature_dir>/tickets/*.md`, never from journeys or chat at publish time. IDs `T-<DOMAIN>-NNN` are stable: upsert by ID, never renumber, reuse or duplicate. | — | publish-tickets |
| **R6** | **Starter workbook is canonical and frozen.** `templates/excel/page-spec-templates.xlsx` is the layout reference; never edit it (copy it to fill a spec by hand). Generated sheets match its layout; only the pastel fills and framework-only blocks differ. | — | `tools/check.py` (starter hash, layout) |
| **R7** | **Specs must validate.** Every page spec validates against `schemas/page-spec.schema.json` (unknown or misspelt fields are errors). The generator refuses invalid specs; `--no-validate` is for drafts only. | — | Generator; `tools/check.py` |
| **R8** | **Feature slugs are unique** across every work folder (`project.work_dir`, `output.work_dirs`, `output.work_dir`). Before creating a feature, check the slug exists in none of them; a lookup that finds two folders is an error, not a choice. Features are never moved between work folders. | — | `tools/check.py` (slugs) |
| **R9** | **Edit safely.** Follow `AGENT-BRIEF.md` → Editing rules (re-read and hash-check before writing, targeted edits, UTF-8 without BOM, keep line endings, run `tools/check.py`). | — | `tools/check.py` (encoding); `.editorconfig` |
