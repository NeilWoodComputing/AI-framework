## User story

**As** the owner of API.Framework  
**I want** the API's own names to say System instead of Unity  
**So that** the API no longer looks like the real Unity product it was modelled on

## Full-stack scope

No UI controls. Data: seeded rows of `LoginFeatures` (`Api.Framework.Data/LoginFeatures.cs` lines 7, 11, 17) and `LoginPermissions` (`LoginPermissions.cs`: `unity_messenger_dashboard` line 14; group `Unity messenger` on every row that uses it, at least lines 14, 15, 23). Files: `Program.cs:116, 142`, `appsettings.json` / `appsettings.Test.json` lines 6–7, `Api.Framework.Services/Options/JwtOptions.cs:7, 9`, comments in `LoginFeatures.cs`, `LoginPermissions.cs`, `ReferenceDataSchemaBinding.cs:6`, and one new migration under `Api.Framework.Data/Migrations/`.

## Work to do

1. CORS policy `UnityUi` → `SystemUi` (both the `AddPolicy` and `UseCors` calls).
2. JWT issuer / audience `unity-login` → `system-login` in `appsettings.json`, `appsettings.Test.json` and the `JwtOptions` defaults. Values only, no secret touched; existing tokens become invalid (accepted).
3. Seeded names (D15): `UnityBasicFeatures` → `SystemBasicFeatures`, `Unity messenger` → `System messenger`, `unity_messenger_dashboard` → `system_messenger_dashboard`. Change the constants / `Define(...)` rows, then `dotnet ef migrations add RenameUnityToSystem` so the migration updates the rows **by their existing ids**. Never edit old migrations or `.Designer.cs` files (the snapshot is regenerated by the tool).
4. Comments and XML docs that describe the active target → System. Text that names the real Unity.API / Unity UI stays (D10).
5. Never introduce a type or namespace named plain `System`. Leave `using System…`, `TimeProvider.System` and `IsSystemAdmin` untouched.
6. Apply the migration to the Test database and run `dotnet test`.
