# Plan: Manage Animals

## Summary

Administrators need to maintain a catalogue of animals — listing them in a Manage Animals grid and adding, editing, or soft-deleting each record via a Basic Form. Every field persists through the Animals service to the Animal table. Name must be unique (case-insensitive, trimmed) across all non-deleted animals, and Date Born is mandatory and must be strictly before today. Animals have **one permission of their own, `animals_write`** (decisions 22, 24), and every user gets it through the seeded Administrators and Standard groups (decision 25). Without it there is no Animals nav link, the page does not open and the API returns 403; there is no read-only access. Users with it add animals, and Edit / Delete them from a **row actions menu in the Actions column at the end of the grid** (decisions 23, 26). The menu is a reusable, permission-aware grid feature of UI.NextJs.Framework (T-ANIMAL-007). **There is no View Animal action and no View mode** (decision 20, Neil 2026-10-08 14:31 BST). Clicking a row does nothing; Edit is chosen from the row actions menu (Q23). The list is **on the page** `/examples/animals`, not in a modal; only the Add | Edit form and the delete confirmation are modals (decision 27, Neil's standing rule).

### Attributes storage (concrete mapping)

`Animal.Attributes` is a **JSON array of strings** column storing `["nocturnal","endangered",…]`: `jsonb`, NOT NULL, default `'[]'`, the same as the existing `ReferenceDataItem.Attributes` (decision 10). An animal with no tags stores `[]`, never null. The Basic Form uses a **Tag Input (multi-value)** control: users add/remove free-text tags as chips (any characters, ≤ 50 characters each, ≤ 20 tags, no other rules — decision 1); the service serialises the chip list to/from the JSON array. The manage grid displays Attributes as a comma-separated Char column from the same Population Source.

### DB schema `creatures` (decision 21) — how API.Framework assigns schemas today

Checked in API.Framework (read only, no code changed):

- `LoginDbContext` has `public const string Schema = "auth";` and calls `modelBuilder.HasDefaultSchema(Schema)` in `OnModelCreating`, so every entity lands in `auth` unless it says otherwise. No entity uses a `[Table(Schema = ...)]` attribute and no table lives outside `auth` today, so there is no existing example of a second schema.
- Tables are named per entity with `entity.ToTable("<snake_case_plural>")`; columns are snake_case by convention.
- `Program.cs` registers the context with `UseNpgsql(..., npgsql => npgsql.MigrationsHistoryTable("__ef_migrations_history", LoginDbContext.Schema))`, so the EF history table is `auth.__ef_migrations_history`.
- Migrations are applied by the API itself at start-up (`context.Database.Migrate()` in `Program.cs`), using the app's own connection (`LoginConnection`). The initial migration starts with `migrationBuilder.EnsureSchema(name: "auth")`.
- No SQL scripts, grants or `CREATE SCHEMA` statements exist in the repo; database roles / privileges are managed outside it.

### Permissions (decisions 22, 24, 25) — how API.Framework and Next.js do it today

Checked read only (no code changed; no `.env`, appsettings secrets or connection strings opened):

- **Declared** in `Api.Framework.Data/LoginPermissions.cs`: `LoginPermissions.All` is a list of `PermissionDefinition(Id, Name, DisplayName, Category)` built with `Define(number, name, displayName, category)`, which gives a fixed id `00000000-0000-4000-8000-{number:D12}`. Numbers 1–24 are used. Names are snake_case, mostly `<area>_read` / `<area>_write` pairs: `user_management_read` ("View users and groups") / `user_management_write` ("Manage users and groups"), category "User management"; also `dtn_flow_builder_read` / `_write`, `reports_management_read` / `_write`, `dip_service_plan_management_read` / `_write`, and so on.
- **There are no catalogue permissions.** `CatalogueItemController`, `ReferenceDataController`, `ComponentShowcaseController`, the schema controllers and the directory controllers all use `DirectoryPolicies.UserManagementRead` / `UserManagementWrite`. So the "catalogue read/write policies" that decision 22 replaces are the user-management ones (Dev Bot's `AnimalController` and `AnimalSchemaController` use them too).
- **Policies** in `Api.Framework.Services/Directory/DirectoryPolicies.cs`: policy-name constants `UserManagementRead` / `UserManagementWrite` plus permission-name constants `ReadPermission = "user_management_read"` / `WritePermission = "user_management_write"`. `Api.Framework/Program.cs` registers them in `AddAuthorization`: read = `RequireClaim(TokenService.PermissionClaimType, ReadPermission, WritePermission)` (either one), write = `RequireClaim(..., WritePermission)`. `DirectoryPolicies` is the only policy class.
- **Claims:** `Api.Framework.Services/Auth/TokenService.cs` adds one JWT claim of type `"permission"` (`PermissionClaimType`) per permission name. `LoginService.LoadPermissionNamesAsync` builds the list when a token is issued: every permission for `IsSystemAdmin` users, otherwise the union of permissions on the user's permission groups. A user only gets a new permission in their next token (sign in again or refresh).
- **Seeded:** `LoginDbContext` seeds `auth.permissions` from `LoginPermissions.All` with `HasData`, so a new entry becomes an `InsertData` in the next EF migration. `SeededGroupPermissions()` links **every** permission in `LoginPermissions.All` to the preset **Administrators** group (`LoginPermissionGroupIds.Administrators`, default tenant), and only `user_management_read` to the preset **Standard** group (the default group for new users). The seeded system admin user (`DefaultUserSeeder`) is in Administrators and is also `IsSystemAdmin`. The first user to register goes into Administrators, everyone after into Standard (`LoginService`).
- **Assigned:** groups get permissions manually through the directory API (`DirectoryService`, `PermissionIds` on a group; any existing permission id is accepted). For other tenants, `TenantService` creates an "<tenant> Administrators" group with every permission whose `Category` matches one of the tenant's features (`LoginFeatures`, e.g. `UnityBasicFeatures` → "User management", always selected), and re-applies that when the tenant is saved.
- **Next.js:** the signed-in session carries `permissions: string[]` (`src/framework/auth/models/auth-state.model.ts`, mapped in `auth-session.utils.ts`, read with `useAuth()` from `@auth/context/AuthProvider`). There is **no shared permission helper** and `src/shell/components/SiteNav.tsx` does **not** hide any link by permission (it only checks whether there is a session). The only permission checks are Dev Bot's feature-local `src/features/animals/shared/utils/animal-permissions.ts` (`user_management_read` / `user_management_write`), used by `use-animals-grid.tsx`.

Who else ends up in which group (checked read only, for decision 25):

- The preset **Standard** group is the default tenant's only `IsDefault = true` group. Self-registered users go to Administrators (first user) or Standard (everyone after) — `LoginService`, always tenant `LoginTenantIds.Default`. Users created through the directory API with no groups chosen get the tenant's default groups (`DirectoryService.ResolveGroupsAsync(..., useDefaultsWhenEmpty: true)`); with groups chosen, only those groups.
- Other tenants get only an "<tenant> Administrators" group from `TenantService` (`CreateAdminGroupAsync`; the power user is put in it), with the permissions whose category matches the tenant's features. It is recalculated only when the tenant is saved, and there is no Standard group for other tenants. Their ids are created at runtime, so `HasData` cannot seed them.
- The permission list API (`DirectoryService`, ordered by category) lists every permission, and group validation accepts any existing permission id, so any group in any tenant can be given `animals_write` manually.

### Grid Actions column (decisions 23, 26) — how the Next.js `EntityGrid` works today

Checked read only in `src/framework/entity-framework/` (current files include Dev Bot's uncommitted changes listed in `handoff.md` › `implementation`):

Each cell renders every action as a small text `Button` (`buttons`, the default), or Dev Bot's `EntityGridRowActionsMenu` (`menu`: an "Actions" button opening a list of icon + label items). If `rowActions` is empty, no Actions column is rendered. There is no row-click handler.
- Used by: `ReferenceDataTypesGrid.tsx` ("Manage" text button) and `use-reference-data-items-grid.ts` (default `buttons`); `use-animals-grid.tsx` (`menu`, with View / Edit / Delete; Edit and Delete only added when `user_management_write` is present).
- Icons: `src/framework/design-system/components/icon/Icon.tsx` (added by Dev Bot) has `Visibility`, `Edit` and `Delete`. `@design-system` has no Tooltip component.

So the reusable extension point is the existing `__actions` column with Dev Bot's `menu` display (decision 26 keeps it): add permission-aware items (for example `requiredPermissions` on `GridRowAction`, checked against `session.permissions`) and optional per-row visibility, hide the column when no item is allowed, and keep `buttons` as the default so the reference-data grids do not change (T-ANIMAL-007; details per Q32, accepted).
